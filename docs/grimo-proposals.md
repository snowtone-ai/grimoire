## 提案の結論

**A「おかえり、グリモ」を推奨する。** 大きく映る相棒をなでる、食べ物を渡す、そばで休む。タスクを終えた日も、何もできなかった日も、同じように迎える。Bの背景選択とCの思い出を小さく取り入れ、最初から庭づくりや大量の収集を抱えない。

`prompt.md` の今回のOrderは調査と複数企画の提出。画面の実装・研究所の撤去・データ移行・公開は次の段階。追加質問なしで企画可能なため、仮定を明記して進めた。

1枚のJPEGは完成したアニメ素材ではない。実装時は元絵の利用範囲・分離素材の有無を確認し、キャラクター別の透過素材と必要な表情を揃える。単なる画像の拡大縮小だけで完成品質とはしない。追加費用0円を守り、素材が揃わなければ動作の種類を減らして品質を保つ。

## 共通して守る体験

休むほど損をする仕組みを作らない。空腹で苦しむ、病気、死亡、家出、親密度低下、連続ログインのリセットは採用しない。何日離れても「おかえり」で再開できる。これはKinder Worldの復帰の安心感への評価を根拠とする設計判断（P05）。

触れ合いはアイテムなしで何度でも可能。食べ物は違う反応を楽しむきっかけであり、相棒を維持する燃料にしない。成長はゆっくりでも、触った反応はすぐ返す。進行速度への異なる評価を両立させる（P06・P08）。

## A：おかえり、グリモ【推奨】

**価値:** 一日の途中で30〜90秒、好きな相棒に会って一息つく。

**体験の流れ:** 画面を開く → 相棒がこちらを見る → なでる → 目を細めて近寄る → おやつを渡すか、そのまま眺める → 好きなときに閉じる。完了ダイアログで余韻を切らない。

**主要操作:** 相棒をなでる。タップでも同じ反応を得られ、ドラッグは必須にしない。食べ物、背景、相棒の変更は二次操作。成長値を画面中央に並べない。

**育てる喜び:** 体を大きく進化させるより、距離感・仕草・反応が増える。最初は見つめる、少し仲良くなると自分から寄る、さらに好物の反応や寝顔が増える。最終段階でもふれあいは続き、月初に関係が消えない。

**独自性:** クエストで拾う品々とは別に、その日の小さな行動が相棒への小さな贈り物になる。グリモがタスク内容を読み上げたり、達成を査定したりしない。

**弱点:** 同じ反応の繰り返しは飽きやすい。大量アイテム追加ではなく、4匹それぞれの視線・間・仕草と直前の反応を繰り返しにくい制御に制作を集中する。Spirit Cityの収集後の物足りなさ（P03）を、触れ合いそのものの価値で補う。

**負荷:** 3案では小。ただし触れ合いの絵と動きが最大の制作課題。

## B：グリモの小さな庭

**価値:** 自分で整えた場所に4匹が暮らしている喜び。

**体験の流れ:** 庭へ行く → 小物を置く → グリモが寄ってくる → 食べる・遊ぶ様子を眺める → 気に入った場面を残す。

**主要操作:** お気に入りの場所をひとつ整える。配置編集は専用の子画面に分ける。4匹は庭にいるが、狭い画面では選んだ1匹を中心にする。

**育成と報酬:** タスクの小さな行動でおやつや遊具を得る。庭の組合せで仕草が変わり、お気に入りの場所が増える。背景は「窓辺」「木陰」「星夜」などに切替。

**独自性:** 新種を大量収集するより、同じ4匹の共同生活が深まる。背景は単なる壁紙ではなく、座る位置や眠り方が変わる場所。

**弱点:** 素材、配置、同時動作、画面幅対応の負担が大きい。家具を揃える作業が癒しを上回りやすい。初版にするなら自由配置をやめ、固定の置き場3か所から始める。

**負荷:** 大。箱庭の自由度を優先したい場合の選択肢。

## C：グリモと思い出の手帖

**価値:** 自分と相棒が一緒に過ごした時間が、短い情景として残る。

**体験の流れ:** 会いに行く → 触れ合う → ときどき小さな出来事が起きる → 手帖に1場面が残る → 後日見返す。

**主要操作:** 相棒と一緒に過ごす。日記を書くことを義務にしない。記録閲覧は「思い出」という子画面にする。

**育成と報酬:** 初めて食べたおやつ、初めて一緒に見た雨、初めての寝顔などを残す。タスク数だけで進めず、累積のふれあいによって出会える情景を増やす。季節の情景は翌年も出会え、取り逃がし通知を作らない。

**独自性:** 4匹の個性を短い物語で育てる。定型の短文と絵で成立させ、AI会話・日記内容の外部送信を必要としない。

**弱点:** 継続的な情景制作が必要。読み物や図鑑集めが前面に出ると触れ合いが弱くなる。初版では節目の3場面だけに縮小可能。

**負荷:** 中。記録を見返す愛着を優先したい場合の選択肢。

## 3案の比較

数値スコアは実測と誤認されるため付けず、今回の目的との適合を相対比較した。

| 比較軸 | A：ふれあい | B：小さな庭 | C：思い出 |
|---|---|---|---|
| 疲れた直後に楽しめる | 強い・すぐ触れる | 中・配置が手間になる | 中・読む負担がある |
| 相棒そのものへの愛着 | 強い・反応に集中 | 強い・共同生活 | 強い・記憶が積み重なる |
| 自分だけの空間 | 背景選択に限定 | 最も強い | 中 |
| 1か月後の変化 | 仕草の質に依存 | 組合せが多い | 情景数に依存 |
| タスク管理を圧迫しない | 最も守りやすい | 編集へ長居しやすい | 閲覧へ寄り道しやすい |

推奨はA。Bの背景選択とCの節目記録は、Aの触れ合いが成立したあとに小さく追加する。3案を全部合体させない。

## 推奨案の初版仕様

### 画面と30秒の演出

上部に「グリモ」と設定入口、中央に大きな相棒、下部におやつへの入口。1枚の連続した背景を主役にし、カード群・ステータスパネル群を並べない。操作面は角丸0。キャラクターの自然な丸い輪郭はそのまま使う。

入室で目が合う → なでると顔や体が応える → 手を離すと余韻を残して戻る。相棒の動きが操作の返答を兼ねる。ハートや文字を大量に噴出させない。停止中も寝息・目線などの小さな変化で存在を感じさせるが、reduced-motionでは静止表情で伝える。

世界観は既存Grimoireの魔法と本から続く「相棒と休む私的な場所」。文字よりキャラクターが先に目に入り、既存フォント・色・部品を使う。音は初期OFF、必要な効果音のみ既存の適法な素材から選定する。音なしでも反応が分かる。

### 食べ物の配布案（数値は初期仮説）

| 行動 | 配布案 | 二重配布を防ぐ単位 |
|---|---|---|
| その日に初めてアプリを開く | おやつ1個 | 端末内の日付につき1回。ログイン契約は追加しない |
| その日の最初の手動タスク追加 | おやつ1個 | 日付につき1回。削除・再追加・一括取込で増やさない |
| タスク完了 | おやつ1個、1日3個まで | 通常タスクはIDにつき生涯1回、繰返しはID＋対象日につき1回 |

計1日最大5個。初回に3個を贈り、使い道をすぐ試せる。追加の配布量や所持上限は試遊で調整する。上限で既存の所持品を切り捨てない。食べ物がなくてもなでる・眺める・休むことは常にできる。

食品はまず3種類。既存ドロップ・報酬通貨と混ぜず、好物でも効率差は付けない。選択→相棒に渡す→食べる反応を一続きにする。ドラッグに加えて選択＋ボタンでも渡せる。保存が失敗したら食べ物を失わず、再試行できる。

### 育成・背景・設定

- 育成は「慣れる→近づく→くつろぐ」の累積3段階。暫定でふれあった日1・3・7日が節目、連続日数は不要。連打しても成長を早めず、触れ合い自体は制限しない。
- 各キャラに通常・なでる・食べる・くつろぐの反応を用意。新しい反応の解放を育成の成果とする。見た目を別生物へ進化させない。
- 背景は最初から2種、節目で1種の計3種を候補とする。獲得条件を明示し、変更前に見られる。素材品質が不足する場合は1種で開始し、無償で追加できるまで待つ。
- グリモ画面から「グリモの設定」へ入る。相棒、背景、音、動きの抑制をここで設定・保存する。全体設定の文字サイズとOSのreduced-motionを尊重する。
- 節目の思い出はまず3件までの提案。任意の閲覧のみで、毎日のチェックリストにしない。

初版の対象外: 自由な家具配置、対戦、ランキング、オンライン交流、通知での呼戻し、ガチャ、課金、AIチャット、音声会話、複雑なミニゲーム、無限の物語生成。

## 既存実装からの移行方針

現状は `/plant` の `PlantScreen` と `usePlant` が月ごとの植物を表示し、ナビは「研究所」。`taskDb.ts` には植物進捗の同期があり、IndexedDBとバックアップには `plantState` が含まれる。

実装時は表示・ナビを「グリモ」へ置換し、旧 `/plant` の入口を維持してブックマークを壊さない。植物の育成画面と同期への依存を外す一方、既存の植物記録・報酬・タスクを削除しない。研究所機能の廃止と保存済みデータの破棄は別判断とする。

新しいふれあい記録・所持品・受取履歴・設定は既存Dexieへ必要な分だけ追加する。配布と履歴、消費と反応の確定は同じトランザクションで扱う。複数タブ、再読込、完了取消→再完了で重複しないことを検証する。ローカル時計の変更を完全に防ぐサーバーは設けない。

バックアップは新旧形式の読込、新形式の書出し、旧バックアップの再取込で所持品が増えない方針を先に定める。現在のupsertをそのまま新しい残高へ適用しない。rollbackは追加schemaを認識する互換版を使う。旧版へ戻すためのDB削除は禁止。

新しい外部API、サーバー、常時生成処理は不要。既存Next/React/CSS/Dexieを使い、非表示時は動きを停止する。画像・動き・音の出典と利用範囲を実装段階で記録する。既存ゲームの画像や楽曲は転載しない。

## 実装時の受入条件

1. 4匹の名前・色・輪郭が提供画像と一致し、タップ／キーボードだけでも相棒を選び、なで、おやつを渡せる。
2. 初回から反応を楽しめる。7日空けても所持品・関係が減らず、食べ物0個でも触れる。
3. 配布の二重計上、消費の二重処理、保存失敗時の紛失がない。新旧バックアップを往復して既存データを保持する。
4. 背景・相棒・音が再読込後も保持され、音OFF・reduced-motion・文字サイズLargeが反映される。
5. Chrome DevToolsで320/390/1280px、低い画面、キーボード、console/network/runtimeを確認する。押下の視覚応答100ms以内を暫定目標として実測し、重い素材は調整する。
6. 連続して触れても処理が詰まらず、非表示時に不要なアニメループが止まる。主要操作と保存に応じたテスト・通常verifyを行う。
7. 試遊で「触る前より気持ちが休まるか」「反応が同じで飽きるか」「日課として義務に感じるか」を直接聞く。滞在時間や完了数だけを成功指標にしない。外部の行動計測は追加しない。

## 次の段階

Aを基準とする実装依頼を受けたら、まず1匹の「なでる→応える」を実画面で作り、質を確かめてから4匹・食べ物・保存へ広げる。全機能を作ってから触り心地を評価する順序にはしない。元絵の利用範囲と分離素材の状況に不明点が残る場合だけ、その時点でまとめて確認する。
