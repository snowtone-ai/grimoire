# ポケモンSVの触れ合いからグリモを再設計する

調査・設計日: 2026-09-08 JST。状態: 調査に基づく提案。製品への実装・採用・公開は未実施。

対象は『ポケットモンスター スカーレット・バイオレット』のピクニックでポケモンと過ごす体験。剣盾のキャンプ、XYのポケパルレ、サン・ムーンのリフレッシュをSVの機能として混ぜない。利用者指定に従いmain agentが調査・統合した。出典、媒体別の取得状況、閲覧の限界は [根拠台帳](grimo-picnic-evidence.md)。

## 1. 結論

2026-09-09の利用者補足: スマートフォンの中で癒されるための触れ合いに限定する。歩行・移動・経路探索・自由カメラ・複数体の活動は不要。SVの触れ合いにおける部位への気付き、表情、身体の返事、余韻を手本にする。以下の移動や広い視点に関するBの利点は比較情報であり、実装要求ではない。

グリモが目指すべきものは、**自分の身体と関心を持つ相棒が、こちらの働きかけに気付き、その子らしく返事をする体験**である。触る操作に応じて周囲の装飾が動くだけでは成立しない。

今回の現行実装は、この中心をまだ作れていない。キャロルは一枚の透明PNGで、表情・頭・耳・体を独立して演じる素材がなく、反応は全体位置と雲・星の変化に偏る。「反応の名前が9個あること」を「9つの演技が成立したこと」と扱った点も誤りだった。

推奨は、**既存PWAとThree.jsを活かし、グリモのキャラクター資産・演技・行動制御を作り直すこと**。追加の「事前生成アニメ」「無料」「速度優先」条件を踏まえ、最初はGPT Imageによる少数の表情・決めポーズと2.5D制御を組み合わせ、必要な大きな演技だけ短編クリップを加える。SVに近い身体の向き・接地の自由度まで求める場合は「カメラを限定した3D再構築」が本命となるが、最初の成果を全身3D完成まで待たせない。最新の方式比較・無料条件・第三案Cは [無料アニメーション比較](grimo-free-animation-options.md) を優先する。

「0から」は、タスク管理・IndexedDB・認証・PWAまで捨てる意味ではない。問題があるグリモの表現系を作り直す範囲に限定する。追加支出0円、1体ずつの専用世界、罰や日課なしという既存条件を引き継ぐ。

## 2. 調査の分け方と完了条件

### 調査順序

1. **製品の事実を固定**: 公式説明で実在する操作、場、結果を確認する。
2. **制作方法を確認**: 制作参加者の発言からモデル・表情・演技・遷移の工程を調べる。
3. **観察を照合**: 公式画像、プレイヤーの写真、YouTube、SNSを追い、目に見える事実と解釈を分ける。
4. **体験を分解**: 下表の12分野で、どの知覚・判断・行動が必要かを分析する。
5. **現行コードを監査**: 素材・入力・演技・待機・中断・アクセシビリティの実態を照合する。
6. **方式を設計**: 改善案A・再構築案Bと、追加依頼の事前生成案C・ハイブリッドDについて、再利用範囲、作る資産、制作工程、限界、受入条件を示す。

## 3. SVについて確認できた事実

### 3.1 場・操作・結果

ピクニックには、同じ場で自由に過ごすポケモン、個別の会話、おもちゃ、洗う行為がある。ウォッシュはスポンジとシャワーを使い、きれいになることに加えて回復・絆に結び付く。撮影も用意されている。[公式・触れ合い](https://www.pokemon.co.jp/ex/sv/ja/features/221006_03/)、[公式・ピクニック](https://www.pokemon.co.jp/ex/sv/ja/features/221006_01/)

公式のヌメラの画像を比較すると、洗っている時は閉じ目と泡、完了時は開いた目・大きく開いた口・光と音符が見える。顔の状態と行為の結果が同時に変わっている。静止画であり、変化までの秒数は不明。[洗う画像](https://www.pokemon.co.jp/ex/sv/assets/img/features/ja/221006_03/features_img_05.jpg)、[完了画像](https://www.pokemon.co.jp/ex/sv/assets/img/features/ja/221006_03/features_img_07.jpg)

動画作者レウン氏の本人記事では、洗う相手や部位によって異なる反応が写真付きで記録されている。例えばイッカネズミでは子をかばうという解釈が添えられる。ここから取るのは「部位に意味がある」という設計上の示唆であり、非公開の判定領域や不快度の数式ではない。[本人の観察記録](https://www.gamememory.jp/entry/2023/07/05/203607)

### 3.2 公開されている制作技術

制作担当者の一次証言では、SVのキャラクター制作は、形状と可動域、顔の関節、表情プリセット、個性を確かめる演技試作、アニメーションの状態・遷移設定を伴う。顔の一部表現には関節だけでなくUVスクロールも併用する。したがって「SVは全表情をモーフだけで作る」「1枚絵を揺らしている」とは言えない。[制作担当者PART1](https://cgworld.jp/article/202304-pokemon1.html)、[PART2](https://cgworld.jp/article/202304-pokemon2.html)

表情と体と動きの流れを一貫して作る体制も説明されている。公開された制作規模は、1体の動作を揃えることが本格的な資産制作であることを示す。記事のモーション数は戦闘などを含み、ピクニックだけの本数ではない。[PART3](https://cgworld.jp/article/202304-pokemon3.html)

### 3.3 わからない内部実装

以下は公開一次資料で特定できていない。

- ピクニック専用の行動木・状態機械・優先度の実装形式。
- 好む部位の形状、接触の連続時間、行動抽選の確率、性格との正確な対応。
- 泡や汚れを頂点・UVマスク・別mesh・decal等のどれで保持しているか。
- 接触反応でIKや物理シミュレーションをどこまで使うか。
- 使用エンジン名と、ピクニックの音・アニメーション同期の細部。

後述のraycast、モーフ、状態機械などは**グリモに適した実装提案**であって、SVの内部再現を断言するものではない。

## 4. どのような体験を与えるか — 設計上の解釈

以下は公式機能と利用者記録に基づく分析仮説。愛着や癒しの効果を実験で証明したものではない。

### 4.1 こちらが触る前から、相手には時間がある

ただ入力を待つ対象には「ボタン」の印象が残る。眠り、姿勢、周囲への関心があると、利用者は生活の一場面に参加する感覚を持ちやすい。寝姿を集める本人の写真記録は、無操作時間にも観察する価値がある例だ。[白湯の記録](https://note.com/sayu_7373/n/n605d06a82159)

グリモでは、雲が動くこととキャロルが生きていることを分ける。キャロル自身に「月を見ている」「まどろんでいる」「足を落ち着けている」と読める小さな行動が必要。

### 4.2 自分の行動と相手の返事がつながる

因果を読める場所は、入力した指と相手の身体である。顔を触って背景の星だけが大きくなっても、そのつながりは弱い。触れた側の耳が動く、顔が指へ向く、目が細くなる、押された体が支え直される、といった応答が中心になる。

同じ接触でも、意味が違えば演技が違う。「左だから左へ移動」だけでは方向差であり、個性差ではない。顔は注意、毛並みは心地よさ、足元は重心、飾りは大切な持ち物、というように部位ごとの意味を定める。

### 4.3 表情は結果ラベルでなく、行動の理由を伝える

いきなり笑顔へ切り替えるだけでは「成功マーク」に見える場合がある。まず相手を見る、意味を受け取る、表情が変わる、姿勢がついてくる、という時間的な関係を作る。ただし入力の返事を長い予備動作の後に置くと操作が鈍くなる。

ここで守るのは「同じキャラクターに見える」こと。元画像の目と口の全画素を常時固定することではない。中立顔を基準にした表情の設計が必要になる。

### 4.4 世話は、手を動かした結果が読める

ウォッシュから借りる価値は、スポンジそのものより、触った場所に変化が残り、終わりを身体で返す構造。グリモでは、ブラシで毛が整う、付いていた雲の粒がほぐれる、といった無理のない体験へ置き換えられる。

常時汚して義務を作る必要はない。きれいな状態でも触れ合え、いつ中断しても損をしない。道具を使わなくても相棒に会う価値を保つ。

### 4.5 小さな意外性を、その子らしさとして受け取る

異なる寄り方を性格として解釈している本人記録がある。ただし内部の「せいかく」値と動作が因果的につながる証明ではない。[オルカの記録](https://note.com/gps374/n/n8e053a1419a7)

グリモでは、同じ入力に完全ランダムで別の動作を返す必要はない。キャロルはゆっくり受け止める、ピノは先に対象を見る、といった意味の一貫性を持たせ、その範囲で目を閉じる長さや耳の動きを変える。

### 4.6 参考製品の弱点も引き継がない

プレイヤーには「直接なでたい」「個別の触れ合いが少ない」という不満もある。[直接なでることへの要望](https://www.reddit.com/r/pokemon/comments/z173ya/can_you_still_pet_your_pok%C3%A9mon_in_sv/)、[触れ合いへの不満](https://www.reddit.com/r/PokemonScarletViolet/comments/17e3ifa/picnics_are_disappointing/)

グリモは、1体への直接接触をすぐ始められることを強みにする。タマゴ、食材消費、食事パワー、複数体同時表示、複雑な調理は今回の目的に不要。罰をなくしても、くすぐったく身をすくめる、飾りをそっと守るなどの反応差は作れる。強い拒絶・好感度減少・機能ロックに結び付けない。

## 6. 両案に共通する体験・演技仕様

以下の数値・動作は**グリモ用の初期提案値**。SVから測定した数値ではなく、試作の実機確認で調整する。

### 6.1 30秒のキャロル体験

| 場面 | キャロルの行動 | 利用者が読み取れること |
|---|---|---|
| 開く | 雲に落ち着いている。短くこちらへ視線を寄せる | 会いに来たことに気付いた |
| 頭へ触れる | 接触側の耳と目が先に返答し、頭が少し下がる | 触れた場所が伝わった |
| 毛をゆっくりなでる | 目がやわらぎ、体重を触れた側へ少し預ける | この触り方が心地よい |
| そっと押して待つ | 体が受け止め、足と雲が重みを支える | 単なる画像の移動ではなく身体がある |
| 指を離す | すぐ真顔に戻らず、短く余韻を残して落ち着く | 行為が途中で消えていない |
| 何もしない | 月へ視線を戻す、ゆっくり瞬きするなど、穏やかに過ごす | 入力しなくてもここにいる |

30秒はレビューする場面の長さであり、自動進行する固定ムービーではない。どの時点からも利用者が介入できる。

### 6.2 表情を先に設計する

最初に必要なのは「中立・注意・心地よい・小さな驚き・まどろみ・瞬き」の6状態。喜怒哀楽を機械的に一式揃えるより、キャロルの触れ合いに使う表情を優先する。

各状態について、両目の開き、視線、口、頭、耳の組合せを決める。目だけ・口だけを無制限に組み合わせず、不自然な組合せを避ける。瞬きと心地よい閉じ目が競合して突然目が開かないよう、まぶたの最終値を1箇所で合成する。

中立状態では原画の目の間隔・顔の比率・配色・装飾を参照する。表情状態では意図した変化を認める。全画素一致による原画ファイルの保全試験と、可動キャラクターの見た目の受入試験を分ける。

### 6.3 接触は「場所・動き・文脈」で判断する

入力から演技までを次の一方向で扱う。

```text
画面上のpointer
  → 現在のキャラクターへの交点
  → UV / 部位 / 最近の速度 / 継続時間
  → 触り方の判断
  → 個体の関心と現在演技に応じた返事
  → 顔・頭・体・道具・音の協調
  → 解放後の余韻
```

2D案でも画面の区分をそのまま顔判定にしない。カメラと現在の変換を逆にたどり、絵のUVへ変換する。3D案はraycastの交点・UV・部位IDを使う。透明面はalphaだけでなく部位maskで除外する。細い飾りには触りやすい余裕を持たせつつ、顔と取り違えない。[Three.js Raycaster](https://threejs.org/docs/pages/Raycaster.html)

ジェスチャーは、短いtap、低速で連続したstroke、移動の少ないholdに分ける。速度は直近の短い区間で求め、端末のpointerイベント数に依存する単純な回数判定を避ける。ドラッグは「指に沿って相棒を持ち運ぶ」と決めつけず、毛や頭が指を追う行為にする。身体を移動させる操作を追加するなら、別の意図と可動域を定義する。

### 6.4 反応を途中で再生し直さない

入力直後の返事と、少し遅れて出る全身演技を分ける。仮目標は、入力から知覚できる最初の変化までp95で100ms以内。表情・姿勢の主反応はその後おおむね150〜600msの幅で演出し、離した後はおおむね0.5〜1.5秒の余韻から調整する。

この時間は待ち行列を作るためのものではない。新しい入力が来れば現在姿勢から方向を変えられる。`release`は指の所有を解放し、演技を余韻へ移す。`cancel`は中断として扱い、完成したなで動作の報酬や満足演技を勝手に発火しない。

背景の反応は、身体の反応を支える位置と時刻に置く。雲が沈むなら足元、光が返るなら触れた装飾。画面全体で同時に反応すると主役が読みにくくなる。

### 6.5 少数の状態で自発性を作る

キャロルの最初の行動状態は `落ち着く / 周囲を見る / こちらを見る / 触れ合う / まどろむ` で足りる。疲労・空腹・好感度の減点を実装する必要はない。

選択に使うのは、最後に触れた場所、触り方、直前にした演技、経過時間、道具の位置、その子の性格。短期記憶はsession内で足り、全操作履歴を保存しない。行動が毎フレーム変わらない最短継続時間と、同じ演技を続け過ぎない条件を設ける。優先順位は、解除・中断の処理、現在の接触、明示的な道具操作、自発行動の順を基本にする。

AI会話APIやLLMはこの判断に必要ない。ローカルの規則と少数状態で、理由のある反応を作れる。「自発的に見える」と「高度な推論をしている」は別である。個性・自発性・観客の納得感を重視する考え方は、信じられるキャラクターの研究とも整合する。[CMUの研究](https://www.cs.cmu.edu/Groups/oz/papers/CMU-CS-97-156.html)

### 6.6 視線・姿勢・音を協調させる

視線の対象は利用者、接触点、道具、世界の関心対象から選ぶ。常時pointerを追うと監視される感じや眼球の機械的な動きが出るため、視線が落ち着く時間を設ける。

顔、頭、体、耳、装飾は同じ位相のsin波で揺らさない。頭が向いた後に耳が落ち着く、体が沈んでから毛が少し残る、といった役割のある時間差を使う。二次動作は主動作が読める範囲に抑える。アニメーション制作でのタイミング・予備動作・余韻・二次動作の原則を参照する。[Disney Animation](https://www.disneyanimation.com/process/animation/)

音は「接触した瞬間の小さな音」「相棒の返事」「場の環境音」を分ける。鳴き声をpointermoveごとに鳴らさず、演技の決めた時点で1回発火し、連打時は重なりを制限する。既存の音設定を尊重し、無音でも表情で伝わる設計とする。[Web Audio公式実装資料](https://developer.mozilla.org/en-US/docs/Web/API/Web_Audio_API/Best_practices)

## 7. A案 — 現行を改善する2.5D方式

### 7.1 何を残し、何を作るか

残すものは、Next.jsの画面枠、Three.js、既存の背景・色、元の原画、pointer所有権の考え方、キーボードの代替操作。新たに作るものは、動かせるキャロルの素材、部位判定、表情・演技、解放と自発行動の制御。

一枚絵から、頭・顔・耳・胴・足・飾りを必要な単位で分ける。最初から全部を分離するのではなく、6.1の演技に必要な部位に限定する。隠れていた輪郭や、目を消した下地は原画に存在しないため、単に画像を切り取るだけでは完成しない。

### 7.2 資産制作手順

1. 元絵を基準として保全し、各可動部の境界・支点・前後関係を定める。
2. 顔の下地と6表情、動く部位の隠れ面を制作する。同じ画風の整った素材として目視確認する。
3. 中立状態を再合成して、切れ目・二重輪郭・余白・色のズレを確認する。
4. 全可動域の両端でも、穴・重なり・線の引き伸ばしが出ないか確認する。
5. 3つの接触演技を作り、既存1枚絵版と同じ大きさ・背景で比較する。

原画の不足は制作作業として引き受ける。生成候補が1回失敗したことを理由に利用者へ表情素材の用意を丸投げしたり、表情を省略して完了したりしない。ただし、良い素材が完成していない時点では未達と報告する。

### 7.3 描画と動き

Three.js内の少数plane/meshを親子にし、頭の移動に耳と顔がついてくる構造を作る。表情は同じ位置に揃えたatlasを基本とする。全顔の単純な長いcrossfadeは二重目に見えるため、短い切替か中間表情でつなぐ。毛の局所mesh変形は顔・目に影響しないmaskに限定する。

行動選択は第6節を使い、rendererへ「表情、頭角度、重心、耳、接点」といった値を渡す。雲の強さを変えて顔の反応不足を補う調整はしない。

### 7.4 成立する体験と限界

正面または固定の斜め視点での、なでる、つつく、押す、瞬き、視線、小さな姿勢変化には適する。元絵の画風を残しやすく、既存ページへの統合範囲も比較的小さい。

一方、横を向く、背中を見る、歩いて近づく、大きく伏せる、物を身体で運ぶ、といった場面は追加原画や別姿勢が必要になる。1視点の絵を強く変形して360度の動きを作ろうとすると、原画を崩す。SVの空間的な触れ合いと同じ範囲には到達しない。

**Aを選ぶ条件**: 画面の中の絵本の相棒に触れることが最重要で、自由な向き・歩行・観察距離の変化を求めない場合。

## 8. B案 — キャラクター表現を0から再構築する限定3D方式

### 8.1 目標

キャロルが雲の上に実際の身体を持ち、頭を向け、体を支え、軽く姿勢を変え、視線と顔で返事をする。最初のカメラは原画に近い斜め正面に限定し、自由な360度カメラや広い移動空間は後回しにする。

使用候補は、ローカルのBlenderでの制作、glTF/GLB、既存Three.jsのGLTFLoader・AnimationMixer・SkinnedMesh。骨格と顔のモーフや関節を組み合わせられる。[Three.jsアニメーション](https://threejs.org/manual/en/animation-system.html)、[glTF仕様](https://registry.khronos.org/glTF/specs/2.0/glTF-2.0.html)

### 8.2 3D化の本当の難所

原画1枚は3Dの設計図一式ではない。横顔・背中・口の内側・耳の付け根・脚の付け根・装飾の厚みには未定義部分がある。AIやモデリングで自動補完しても、それは新しい設計判断になる。

そのため、**顔と全体の静止見た目を通さず、歩行や大量演技に進まない**。時間をかけられても、この工程を飛ばすと動く別キャラクターが出来上がる。元PNGに似た見た目を保証するのではなく、原画と比較して採否を判断できる試作を作る。

### 8.3 制作工程

| 段階 | 作るもの | 合格条件 |
|---|---|---|
| B0 見た目の基準 | 原画の特徴一覧、参照カメラ、少数の向きと表情設計 | 同一性を保つ条件と意図的に動かす条件が明確 |
| B1 静止モデル | キャロル1体の形状・UV・材質 | 参照視点でキャロルに見える。主要輪郭、色、顔、装飾が不自然でない |
| B2 顔の試作 | 中立・注意・心地よい・驚き・まどろみ・瞬き | 表情が読めるが別個体にならない。目と口が体に貫通しない |
| B3 身体の試作 | 頭、胴、耳、足、飾りの最小リグ | 触れた側へ向き、体を預けて支え直せる |
| B4 30秒触れ合い | 3操作、解放、短い待機、視線の統合 | 説明を消しても反応差がわかる |
| B5 専用世界 | 雲床、影、奥行き、1つの小道具 | 身体と接点の理解を助ける |
| B6 製品化 | 入力中断・音・性能・offline・復旧 | 第12節の受入を満たす |

B1/B2で原画の魅力を保てない場合は、その時点で素材を調整するかA案へ戻す。動かせることを理由に見た目の問題を押し切らない。A/Bを同時に最後まで作る計画にはしない。

### 8.4 リグとアニメーション

体の大きな動きは骨格、顔はプリセット化したモーフまたは関節、漫画的に幾何で表しにくい目はテクスチャ表現を必要時だけ併用する。SVと同じ実装を選ぶためではなく、キャロルの絵柄が壊れない最小の組合せを選ぶ。

顔と体は別々に勝手なタイミングで再生しない。演技1件に「視線、顔、頭、重心、耳、音イベント」をまとめ、必要なchannelだけ現在状態へ重ねる。clipの切替はブレンドし、終了時に無条件で初期ポーズへsnapさせない。

足元は床に接していると読めることを優先する。まず制作した接地の動作と限定された床で成立させ、地形に合わせる必要が実際に出た時だけIKを導入する。羊毛の全面物理・毛の一本単位の計算・流体シミュレーションは初版に必要ない。

### 8.5 世界とカメラ

カメラはキャロルの顔と触れる部位が同時に読める距離にする。接触のたびに自動ズームや大きなカメラ揺れを起こさない。地面または雲床に重心と影を置き、上下移動が単なる浮遊に見えないようにする。

正投影か弱い透視投影かは、B1の見た目比較で決める。今の正投影cameraを使うことも可能であり、3D化が即リアルな絵柄や自由カメラを意味するわけではない。

SVの多体の社会行動は、既存の「1体＋専用世界」と衝突するため初版へ移さない。その代わり相棒が世界の小さな物へ注意を向ける時間を作り、独立した生活感を持たせる。

### 8.6 道具の導入

最初は裸の指での触れ合いを成立させる。その後、キャロルに合うブラシ等を1つ加える。道具の移動、道具を見る視線、触れた部位の変化、相棒の返事を一つの流れにする。

表面に残る変化が必要なら、UV上の小さなmaskや部位状態から始める。完全な洗浄流体は不要。小道具を投げて遊ぶ場合も、限定床上の簡単な運動と追視・接触演技を先に作り、汎用物理engineを先行導入しない。

### 8.7 Webへの統合

Next.js側は相棒選択・音設定・アクセシブルな操作と読み込みを持つ。毎フレームの骨格・顔・視線更新はThree.js側で行う。runtimeの内部は、入力判断、行動選択、演技の合成、描画・音の役割を分けるが、最初から汎用engineやplugin機構を作らない。

GLBとtextureは選択中の1体を優先して読み、5体を同時にGPUへ常駐させない。初回にcached shellがない完全offlineまで保証しない。既存PWAへ資産を追加する段階で、cache容量と更新・旧版復帰を検証する。グリモの失敗でタスク画面を巻き込まない。

保存が必要なのは選択中の相棒や音の好みなどから始める。触るたびにIndexedDBへ書かず、schemaとbackup変更を避ける。必要が生じた段階で後方互換性を確認する。

## 9. A/B比較と技術選定

以下は実装前の適合性判断。性能実測や費用見積もりの完成値ではない。

| 比較軸 | A: 2.5D改善 | B: 限定3D再構築 |
|---|---|---|
| 元絵の画風の保持 | 有利。ただし追加表情・下地の制作が必要 | 材質・形状・照明の調整が難所 |
| 明確な表情変化 | 可能 | 可能 |
| なでる／押す／部位反応 | 可能。固定視点に強い | 可能。姿勢変化後も空間に対応しやすい |
| 向き・姿勢・移動の幅 | 原画と追加姿勢に制約 | モデルとリグが整えば広い |
| 接地・重み・小道具 | 限定演出で成立 | 身体の動きと揃えやすい |
| 後から視点を広げる | 追加原画が増える | 背面等を仕上げる必要はあるが基盤を共有できる |
| 最初の主要リスク | 分離・補筆と顔の品質 | 原画に似た3Dモデルとリグの品質 |
| 5体展開 | 個体ごとの原画・部位・演技が必要 | 個体ごとのモデル・リグ・演技が必要 |
| 追加支出 | 0円で計画可能 | 0円で計画可能 |
| 人的・制作コスト | 中。無視できない | 大。時間がかかる前提 |
| SVの身体的体験への近さ | 一部を高品質に抽出 | こちらが本命。ただし完成品質次第 |

**最新の推奨はA＋事前生成演技のハイブリッドD**。移動不要・スマートフォンの定位置での触れ合いという補足により、Bの広い可動範囲より、顔・視線・触った部位の演技品質を優先する。Three.jsは維持し、原画一枚を揺らす前提を撤回する。定位置でも頭を傾ける、触れた側へ少し身を寄せる、耳を動かす、といった身体性は残す。Bはそれが2.5Dでは成立しない場合の手段であり、最初の必須条件ではない。

### 他の道具を今の主案にしない理由

- **Godot**: ゲーム制作環境として候補にはなるが、既存React/PWAとの境界やWeb配信を作り直す負担が増える。Three.jsで必要な可動モデルを扱えるため、現段階で移行の必要がない。[Godot Web出力](https://docs.godotengine.org/en/4.5/tutorials/export/exporting_for_web.html)
- **Live2D**: A案に適する専用制作機能があるが、素材不足は別途解決が必要。FREE/PROの差とSDK配布条件を確認して採る選択であり、導入だけで原画が動くものではない。[公式比較](https://www.live2d.com/en/cubism/comparison/)
- **Rive**: 状態を持つ2D表現の候補。runtimeのMITライセンスと、制作・書出しの利用条件は別。今回の既存画像の可動化に対する具体的な優位をまだ確認していない。[公式runtime](https://rive.app/docs/runtimes/getting-started)
- **全反応を動画やスプライトで作る**: 固定演技はきれいに作れるが、途中の接触位置・速度・解放への応答には別設計が必要。主役全体の反応基盤にする前に、その制約を評価する。

Blenderは無償で使用できる制作候補で、出力物へソフトウェアのGPLがそのまま強制されるわけではない。[Blender公式](https://www.blender.org/about/license/)

今回、ツールの追加導入・課金・trial開始はしていない。モデルや表情を商用素材で買う計画にもしていない。0円は追加の金銭支出の条件であり、高品質なモデリングやアニメーションが自動で完成する保証ではない。

## 10. 5体へ展開する方法

共通化するのは「接触の受け取り」「解除と中断」「演技のphase」「資産ロード」「レビュー操作」程度。共通の同一演技へ倍率を掛けるだけにはしない。次表は既存の個性を触れ合いへ落とす提案。

| 相棒 | 先に動く部位・反応 | 心地よさの表現 | 世界へのつながり |
|---|---|---|---|
| キャロル | 耳・目で受けて、頭と体がゆっくり追う | 目をゆるめ、体重を預ける | 雲床が重みを受ける |
| ピノ | 目→頭→手 | 対象を確かめ、触り返したそうに手を寄せる | 泡を目で追い、水輪へ注意を戻す |
| ジル | 胸・頭→翼→尾 | 身を起こして軽く弾み、落ち着く | 苔の沈みと葉の小さな動き |
| シュシュ | 視線で確かめてから頬 | 頬を寄せ、ゆっくり目を閉じる | 花びらが遅れて落ち着く |
| ムゥ | 目と頷き→指揮棒・尾 | 小さな拍で返事をする | 花や音へ一拍遅れで広がる |

キャロルのassetと演技の完成後、体形と動きが異なる1体で共通部分を確認する。それ以前に5体対応の汎用リグ、巨大な反応JSON、制作skill一式を確定しない。登録表が5行あることは、5体が動くことではない。

## 11. 実行順序と成果物

次の実装で最初に渡すべきものは、説明文や大量のsliderではなく、**キャロルの顔と身体の変化が見える短い試作**である。

| 順序 | 作業 | 渡す成果 | 次へ進む条件 |
|---|---|---|---|
| 1 | 原画と可動時の同一性条件を整理 | 比較用の基準画像・少数表情・可動範囲 | 同じ個体として目視判定できる |
| 2 | B1/B2の見た目試作 | 中立と変化後を並べたモデル、短い顔の演技 | 顔の魅力が維持される。未達なら素材を修正 |
| 3 | 1つの「なでる」を身体まで実装 | 接触→視線→表情→姿勢→余韻の操作可能な場面 | 初見で反応が読み取れる |
| 4 | つつく・hold・release・中断を追加 | 入力の差が見える3操作 | 反応の上書き、貫通、取り残しがない |
| 5 | 待機と世界、小道具を足す | 操作しない時間も意味のある場面 | 待機の魅力と即時介入を両立 |
| 6 | 必要な音、端末・PWA確認 | 無音でも使え、対象端末で滑らかな版 | 第12節の技術・知覚受入が揃う |
| 7 | 明示合格後に次の1体 | 個体差を保った共通化 | 原画・演技の品質を下げない |

「表情差分は後で」「先に150反応」「先に5世界」「先にrenderer再比較」は順番として採らない。工程2の見た目が成立する前に、後工程の本数や完成日を確約しない。

従来のG03/G04は、入力試作として再利用し、体験としては未達へ訂正する。最初の人間レビューは可動キャロルで行い、利用者に不足演技をsliderで補完してもらう形にしない。

## 12. 合否判定 — 「何も変わらない」を繰り返さない

### 12.1 見た目と触れ合い

- 文字・音・星の演出を消しても、中立／注意／心地よい／驚きを区別できる。
- 頭・毛・足元を触り比べると、触った部位に関連した本人の返事が見える。
- つつく、ゆっくりなでる、押して待つが、全体移動の大小以外で区別できる。
- 指を離しても主反応が同フレームで消えず、余韻から自然に落ち着く。
- 入力を繰り返しても先頭poseへの跳躍、表情の取り違え、反応の待ち行列が起きない。
- 60秒の無操作で、意味の異なる自発行動を少なくとも2種類確認できる。頻繁に動き回ることは要求しない。
- 中立の原画らしさだけでなく、動作途中の目・口・装飾・輪郭も目視で確認する。

判定はAIのコード確認だけで終えない。まず私が実画面で比較し、その後利用者が同じ操作で判断できる状態を渡す。複数人の試遊をする場合は探索的評価として扱い、小標本から満足率の一般化をしない。

### 12.2 入力・アクセシビリティ

- 320px幅、通常スマートフォン幅、横向き、desktopで、実際に見える部位へ当たる。
- alpha外や背景を触ると、相棒の顔を触ったことにはならない。
- 長押し中の移動、2本目の指、画面外release、pointercancel、blur、非表示で接触が残らない。
- キーボード・単発の代替ボタンから同じ意味の操作ができる。連続ドラッグだけを必須にしない。
- reduced-motionでは大きな移動や揺れを止め、静止表情・接点の変化を残す。
- 見える状態説明文を撤去する要求と、支援技術の操作ラベルを両立する。必要な読み上げは入力ごとに連呼しない。

### 12.3 性能と信頼性

仮の性能目標は、対象端末で入力から視覚反応のp95が100ms以内、継続した操作中に著しいフレーム落ちや停止がないこと。60fpsを狙うが、平均FPSだけで合格にしない。frame timeの分布、長い停止、texture切替時の詰まりを確認する。

測定では、対象端末・OS・browser・build・viewport・cold/warmを記録する。合成PointerEventから次rAFまでの時間を、実タッチから画面発光までの遅延と同一視しない。SVとWeb版のFPSを異なる環境で比べて優越を断定しない。

- 資産未読込・読込失敗を扱い、顔だけ消える、無反応な空白になる状態を避ける。
- 非表示で描画・自発timer・音を止め、復帰時に巨大な時間差を適用しない。
- 相棒切替や画面往復でGPU資産・listener・音が増殖しない。
- offline再訪と更新後のasset整合を確認する。
- 保存失敗で触れ合いが使えなくならず、既存task/plant/reward/backupを変更しない。
- 対象画面のconsole/network/runtime異常を確認する。

実装時の検証は既存コマンドとChrome DevToolsを使用する。今回の変更は調査文書だけなので、アプリのbuild成功や画面の完成を新たに報告しない。

## 13. 最終判断と残る不確実性

SVから学ぶ最も重要な点は、**動かせる顔と身体を制作し、個性のある演技を実際の操作につなげ、途中と終わりまで調整すること**。素材・演技・制御・受入の4つが必要であり、どれかをコード上の反応数で代用できない。

現行改善案Aは、絵の魅力を残した直接接触に集中する方法として成立する。再構築案Bは、身体の向き・姿勢・接地・空間まで含む理想により近い。ただし追加の無料・速度条件を反映した着手順は、AにGPT Imageの表情差分を使い、必要な部分に事前生成案Cを組み合わせるDを優先する。[追加比較と着手順](grimo-free-animation-options.md)。Bは自由な身体性が不足した場合の拡張先とする。各方式のキャロルでの品質はまだ実証していない。

残る主な不確実性は、キャロルの可動素材を原画の魅力を保って仕上げられるか、実機で触感が満足できるかの2点。YouTubeの時間解析、SV実機計測、非公開AI・物理・泡処理は未確認である。これらを「調べたから完成できた」と扱わず、次の制作物と実機比較で埋める。
