# グリモを追加費用0円で動かす — 事前生成・GPT Imageを含む比較

調査日: 2026-09-08 JST。提案であり、生成・導入・製品実装は今回行っていない。最新の取得可能な公式資料を参照したが、全サービスの全アカウント条件を網羅した保証ではない。利用者の速度優先指示により、全候補の実演比較や事前ベンチマークは行わない。

## 結論

2026-09-09の追加条件: **移動は不要。スマートフォン内の定位置で触れ合って癒されることに集中する。** 歩行clip、経路探索、自由カメラ、広いマップは作らない。顔・視線・頭の傾き・耳や毛の局所反応・小さな身じろぎは触れ合いの演技として残す。この条件では固定視点のA＋Cがさらに適合し、全身3Dを先行する理由は弱くなる。

忠実にする対象はSVの素材そのものではなく、触れた部位に気付き、表情と身体が連動し、離した後にも気持ちが残る反応の構造。キャロル固有の顔・性格で作る。静止画から確認できた顔の差と、グリモ向けに提案する時間・部位制御を区別し、SVと同一のタイミングを再現できたとは主張しない。

**最初に作るなら、GPT Imageで表情と少数の決めポーズを用意し、既存Three.jsで部位の動き・入力への即答・演技の切替を制御するハイブリッドが有力。** 全身3Dを作り終えるまで待つ必要も、全操作を動画で作り切る必要もない。これは制作速度・原画の魅力・自由な接触の折衷に関する設計判断で、生成品質の実証結果ではない。

事前生成した短いアニメを再生する第三案Cは十分成立する。ただし「有限の演技を事前制作」は可能でも、任意の指の位置・速さ・長さ・途中変更を全部動画として列挙することはできない。**待機・大きなごほうび演技はクリップ、触っている間はリアルタイム制御**という分担が最も自然。

無料は三つに分ける。①既存契約内の生成、②回数制限付き無料クラウド、③ローカル制作。①も無制限ではなく、②は恒久的な制作能力ではない。③も手元の計算資源・時間・電力を使う。製品実行時は静的な素材だけを配信し、生成APIを呼ばない。制作サービスが終了しても、取得済み素材と利用権が有効なら再生できる。

## GPT Imageは何に使うべきか

公式の現行モデルページはGPT Image 2を案内している。画像生成・編集用であり、時間方向に一貫した動画を直接出すモデルではない。APIのFree tierは非対応なので、APIを無料案として採用しない。[モデル・料金区分](https://developers.openai.com/api/docs/models/gpt-image-2)

現行ガイドでは参照画像を使う編集と、PNG/WebPの透明背景（GPT Image 2ではpreview）が用意される。一方、繰り返すキャラクターの外見の一貫性には限界が明記される。透明出力対応は輪郭の完全一致や編集範囲外の画素保存を保証しない。[画像生成ガイド](https://developers.openai.com/api/docs/guides/image-generation)

この環境には組み込み画像生成があるが、利用者の残枠・課金条件・実際に割り当てられるモデル名は推測しない。実制作では既存契約内の経路だけを使い、枠切れ時に有料APIへ切り替えない。

用途の優先順位:

1. **顔の差分**: 中立を参照し、注意・閉じ目の心地よさ・軽い驚きの少数セット。まず顔の演技が読める状態を作る。
2. **動くための部品**: 頭、耳、胴体、手足を分けた時に不足する隠れ面の候補。生成だけで完成部品扱いせず、元絵と合う部分を採用する。
3. **決めポーズ**: こちらを見る、なでられて目を細める、眠りに落ちる。前後の演技はローカルで作る。
4. **少数コマのループ**: 瞬き・耳の小さな動き。いきなり数十コマの全身spritesheetを一括生成しない。フレームごとのサイズ・位置・顔が揺れると修正費用が増える。
5. **3D制作の参考図**: 側面や背面は「原画から確定した真実」ではなく、採用判断が必要なデザイン候補。

以前の失敗は、生成した全身差分が構図や輪郭を変えたこと。GPT Image自体が使えない証拠ではない。原本は保存し、候補から必要な差分だけを採る工程へ変える。中立の原画を守ることと、動作中の表情を全画素固定することを混同しない。

| C2: AI短編動画 | 全身の豊かな動作候補を短時間で得られる可能性 | 顔の変化、ループ継ぎ目、背景、割り込み | 待機・非接触演技に限定して候補化 |

## 事前生成アニメを破綻させない最小設計

### 動画の本数より接続を決める

最初は「待機の小ループ」「なでられた顔」「つつかれた驚き」の3意味だけを作る。各クリップに基準位置と戻り姿勢を揃え、なでる演技は開始→持続→終了へ分ける。操作時間を固定2秒へ押し込めない。

接触開始時は、読込済みの顔・耳・局所変形で即答する。大きな演技はその後に接続する。再入力は待ち行列へ積まず、持続ループの延長、同じ演技の強さ変更、別の意味への切替として処理する。背景と顔を含む全画面crossfadeは二重像が出るため万能な遷移にしない。

動画・連番の途中で大きく姿勢が変わるなら、当たり判定も変える。最初は姿勢変化を限定し、明らかに見える顔の外を顔判定にしない。必要になってからクリップごとの少数の部位座標を追加する。

### 配信形式

- 短い顔差分・少数コマ: PNG/WebP atlas。既存sharpで切り出し・梱包し、現在使う分だけ読み込む。
- 長い全身演技: 圧縮videoも候補。ただし透明動画の対応・decoder準備・端末差は実装後の対象ブラウザで確認する。背景込み動画を固定世界に使う案ならalpha不要だが、世界のparallaxとの整合が必要。
- GIF/APNG/animated WebPを置くだけでは任意フレーム制御や割り込みの問題を解決しない。高い圧縮率と触感の制御を別に考える。

Three.jsは[VideoTexture](https://threejs.org/docs/pages/VideoTexture.html)を持つ。動画フレームの通知には[requestVideoFrameCallback](https://developer.mozilla.org/en-US/docs/Web/API/HTMLVideoElement/requestVideoFrameCallback)があるが、どちらもシームレスな切替を自動で保証しない。

容量の落とし穴: 512×512 RGBAの90フレームを全て非圧縮でGPUに常駐させると約90MiB、30クリップなら約2.64GiB（mipmap等を含まない）。これは**連番全常駐の計算**であり、圧縮動画の常時メモリ量ではない。PNG/WebPのファイルが小さくても、展開後の量は別。最初から全演技を大atlasへ詰めない。

## 少し変わった、しかし現実的な案

- **顔だけ俳優、身体は操り人形**: 顔は少数の描かれた演技、耳・頭・毛は分割mesh。少ない素材で「本人が返事をした」感覚を狙える。顔境界の継ぎ目は調整が必要。
- **2.5Dのぬいぐるみ舞台**: 正面〜小さな斜めだけを許し、雲の中に足元を自然に隠す。失敗隠しの装飾ではなく、最初から演技できる範囲を美術設計にする。
- **指に合わせて演技の時間を進める**: 肩を寄せる数コマを、経過時間ではなくなでた量で進め、離すと戻す。入力と絵の因果が強い。圧縮videoの頻繁なseekではなく、少数フレームやpose補間で行う。
- **少ない絵＋滑らかな世界**: キャロルは意図的な少コマ作画、接点・視線・雲は滑らかにする。全身30fps生成を必須にせず、画風として成立させる。
- **AI動画から良いポーズだけ採る**: 動画全体の顔ぶれや継ぎ目が悪くても、採用可能な数コマを演技設計の参考にする。出力の利用条件を満たす場合に限る。
- **3Dを配信しない3D制作**: Blenderで柔らかな光・影込みの演技を描画し、PWAには透明連番を置く。モデリング負担は残るが、端末側の複雑さを減らせる。
- **動きの種類ではなく関心を組み合わせる**: 同じ瞬きでも、月を見る→こちらを見る→目を閉じるという順序で文脈が変わる。クリップ数を増やす前に、視線・間・姿勢の組合せを使う。

## 次の実装で最短に進める順序

1. キャロル一体で、表情差分と最低限の可動部を作る。原本は不変の参照として残す。
2. 同じ実装で「つつく」「連続してなでる」「待つ」をつなぐ。release上書き・長押し競合もここで直す。
3. 実画面で表情差、接触と中断、スマートフォン幅、reduced-motion、異常だけを確認する。生成モデル大会や全端末ベンチマークを先に開催しない。
4. 足りない大きな演技だけ短編クリップを追加する。向き・接地の自由度が本当に不足した場合にBの3Dへ進む。

方式を選ぶための調査はここで区切る。次は論文やサービスの追加列挙ではなく、動くキャロル一体で改善を示す段階。今回の依頼は調査・比較なので、未承認の製品実装や外部素材送信には進んでいない。
