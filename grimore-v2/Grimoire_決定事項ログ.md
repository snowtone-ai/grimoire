## C. 生物と世界の関係（★重要な方針転換・確定事項）

**旧方針（撤回）**：「生物と環境が相互作用する一つの生態系」

**新方針（確定）**：
- 背景世界と生物は**完全に別レイヤー**。
- 背景世界＝独立した「美しく、少しだけ動く鑑賞空間」。生物の物理的な影響は受けない。
- 生物＝背景とは無関係に、独立したモーション（呼吸・瞬き・視線など）で「生きてる感」を出す。
- **唯一の接続点**：背景の主光源の方向・色温度と、全体の色調（トーンマッピング／カラーグレーディング）だけを生物側にも軽く反映させる。それ以外の相互作用は無し。目的は「合成感を出さない」ための最低限の統一。
- **カメラ**：背景は完全固定ループ（カメラ操作不可）。スワイプ等の操作は生物のみに対して行う。
- **生物の配置**：背景内の特定の場所への接地感は不要。「フィギュア的」に、背景のどこにいても自然に見えればよい。足元は柔らかい影のみ（台座は無しがデフォルト）。
- **背景の実装方針**：ライブレンダリングのThree.jsシーン（手続き的な霧・光生成）として作る。目指す品質に届かなければ動画ループへのフォールバックを許容。
- **背景ループの動きの豊かさ**：目標は「やや豊か」（霧の流れ＋光の揺らぎ＋浮遊粒子＋水面のきらめき）。低スペック環境（Pixel 7a等）では「最小限版」へ自動縮退。

## E. タッチインタラクション設計（生物への「触れた時の反応」）

技術方針は2層構造で確定。

1. **常時の揺れ（待機中含む）**：業界標準の「スプリングボーン」技術（Live2D/VRM等で使われる質量バネ物理）を採用。毛・耳・尻尾等が動きに合わせて自然に揺れる。部位・材質ごとにパラメータ（硬さ・揺れ幅）を変える（材質別タッチ感＝毛は柔らかい、鱗は硬い等）。
2. **タップ瞬間の反応**：継続的な物理シミュレーションではなく、あらかじめデザインされた短い手作りリアクションアニメーション（沈み込む・驚いて振り向く・目を細める等）を再生。複数パターンをランダムに出し、同じ反応の連発を避ける（My Talking Tom等の実績あるパターンを踏襲）。
3. **トーン**：Talking Tom的な過剰なコメディ演出ではなく、ねこあつめ的な「穏やかな触れ合い」路線。
4. **方針の根拠**：ゼロから独自の物理シミュレーションを設計するのはリスクが高いため不採用。業界実績のある「常時の物理演算（軽量）＋意図的に設計された反応アニメーション」という型を踏襲する。

## F. UI設計

### F-1. タスク管理画面のレイアウト参照
- ユーザー添付の汎用Todoアプリ画像（タブ・リスト・FAB構成）はレイアウトの参考として採用可。ただしモーションの評価が特に高いプロダクトではない。
- **モーションの品質基準**：Things 3（Apple Design Award受賞、洗練されたトランジションで高評価）を基準とする。

### F-2. 「相棒＋世界」画面の戻るUI（★確定・旧2ファイル未記載）

3パターンを比較した上で確定：

| パターン | 挙動 | 採用可否 |
|---|---|---|
| A：タップで消える・出す（写真/動画ビューア型） | 鑑賞は最大限守れるが、発見性が低い | 不採用 |
| B：常時・極薄chrome型（地図/天気アプリ型） | 迷わせないが、鑑賞体験をわずかに削る | ベース採用 |
| C：OS標準ジェスチャー依存型 | 没入度は最高だが実装難度・学習コストが高い | 不採用 |

**確定仕様**：
- 常時、画面下部に半透明のアイコンボタン（矢印のみ、文字なし）を配置。タスク管理に戻るための機能的な導線が常に必要なため、「タップで出す」方式は不採用。
- 通常時は控えめ、タップした瞬間だけパッと光り、その後フェードアウトして余韻を残す（＝「押している間だけ光る」ではなく「余韻を残すタイプ」を採用）。これはE章のグリモのタッチ反応設計（常時控えめ＋タップ時のみ意図的な反応）と同じ思想であり、UIと生物で「触れた時の呼吸」を揃えている。
- **アイコン本体の色は固定**（視認性・機能性を守るため）。**周囲のグロー（光の輪）だけ**、背景の主光源色に連動させる。これによりC章の「唯一の接続点＝光源の色・トーン」という原則とも一致する。
- この確定により、旧「未決定事項」にあった「相棒＋世界画面でのUIの出し方」は**解決済み**。

### F-3. 設定画面（確定）

- 音はBGMと効果音を独立してON/OFFできる。効果音にはグリモの鳴き声、呼吸音、足音、UI操作音を含める。

- **配置**：タスク管理画面のヘッダー右上に歯車アイコンを置く。相棒＋世界画面には追加せず、F-2の戻る導線だけを維持する。

- **テーマ**：ダークモードをv2の前提要件とする。設定画面で「システムに従う」を既定に、明るい／暗いテーマを選択可能にする。相棒＋世界画面では背景世界をテーマで変えず、戻るボタンなどのUI chromeだけに適用する。
- **実装・検証原則**：色は意味ベースのテーマトークンで管理し、画面やコンポーネントへ直接の色値を埋め込まない。OSテーマの変更へ追従し、初期描画時のテーマ反転を防ぐ。両テーマで通常・hover・focus・disabled・エラーなど全状態を確認し、文字と操作要素はWCAG 2.2 AAのコントラスト基準を満たす。UI変更は明暗両テーマで視覚回帰確認する。

### F-4. 画面名称とカレンダーの役割（確定）

#### ホーム／カレンダーのフロントエンド再設計原則

- v1からv2へ流用するのは、ホームとカレンダーで検証済みの機能、ドメイン上の振る舞い、データ、操作フローという「システム部分」である。画面の情報設計、視覚表現、コンポーネント、モーションは、それらを載せる全く新しいv2アプリとして設計する。
- ホームは「今日のタスク管理」のためだけの画面とする。グリモやグリモの育成情報を表示しない。
- 再設計の基準は、既定事項にある静かで上質なUI、物理的な手触りのある反応、世界画面とUIの分離、ダークモードを含むテーマ品質である。v1の外観を踏襲することを目的にしない。
- 以後のホーム／カレンダーの詳細設計では、既存の決定事項から読み取れる品質・演出基準を前提とし、既に決定済みの意図を改めてユーザーに問い直さない。未決定で実装品質に直接影響する選好だけを、具体案とともに確認する。

#### カレンダー画面の役割と基本構成

- カレンダーは、主に未来のタスク・予定を把握するために開く画面とする。今日のタスクを実行・完了する主導線はホームに置く。
- 月表示を画面の主役とし、選択日のタスク・予定は同一画面内の詳細領域で確認・編集できる構成とする。出所ラベルは表示しない。

### E-4. タップ反応の役割（確定）

- グリモへのタップ反応は、愛着を生むための演出だけであり、タスク進行、成長、報酬、好感度その他のゲーム状態を変化させない。
- 何度触れても楽しめる反応として扱い、操作上の報酬や不利益を設けない。
- 反応は、タップ位置と直前の反応を考慮して複数の短い仕草から選ぶ。同じ反応の機械的な連続再生を避ける。
- タップ反応はエリアと結び付けず、犬グリモ全体で共通の反応ライブラリを持つ。エリア数や解放状況に左右されず、多様な仕草そのものを鑑賞できるようにする。
- タップ反応には、控えめな鳴き声、呼吸音、足音など、環境に馴染む音を含める。設定から音をON/OFFできるようにする。
- 初期版の連続タップ反応は、耳、視線、呼吸、あくびなど、位置移動を伴わない上半身中心の短い仕草に限定する。寝返りや歩行など全身の大きな動作は、専用リグとアニメーションクリップの品質を確保できる段階まで追加しない。

### E-5. スプリングボーンの基本方針（確定）

- 耳、しっぽ、毛先には常時ごく弱い追従を入れる。主な揺れは、呼吸、首振り、タップ反応といったグリモ自身の動作で発生させる。
- 風など環境由来の揺れは、存在を主張しない程度に抑える。常に大きく揺らして玩具のように見せない。
- 剛性、減衰、重力、揺れ幅の数値は、モデルの部位ごとの長さ・重さに依存する。試作モデルでの実機確認を経て決め、決定事項ログには根拠を添えて追記する。
- モーション軽減設定では、スプリングボーンと待機動作を止め、タップ時は静的な表情変化と最小限の反応だけを残す。OSの `prefers-reduced-motion` を初期値に反映し、アプリの設定画面からいつでも上書きできるようにする。

### E-6. タップ反応の実装構成（確定）

- 3D描画は `three` と `@react-three/fiber`、GLB読込・クリップ制御は `@react-three/drei` の `useGLTF` と `useAnimations` を用いる。
- 待機、短いタップ反応、復帰は Three.js 標準の `AnimationMixer` でクロスフェードする。スプリングボーンは物理エンジンを追加せず、部位限定の専用制御とする。
- UIアニメーションは `motion` だけが担当し、3Dアニメーションには用いない。反応選択は外部状態機械ライブラリを導入せず、型付きの小さな反応コントローラで管理する。

### F-5. エリア選択の主体（確定）

- 背景世界（エリア）は、グリモが自律的に移動して変わるものではない。ユーザーが能動的に選択・変更する。
- エリア遷移は、グリモの旅や歩行を表すのではなく、ユーザーの明示操作に応じた環境の切替として設計する。
- 初期版の全エリアは、進行条件やタスク達成報酬にせず、最初から選択可能にする。背景は鑑賞と気分転換のためのものである。

### F-6. グリモ画面の常設操作（確定）

- グリモ画面にも、ホーム、カレンダー、グリモ、図鑑、設定を切り替える共通の下部ナビゲーションを表示する。透明でファンタジー感のある表現とし、背景世界に不自然な不透明UIを重ねない。
- エリア選択は、下部ナビゲーションの直上にある右下の透明なアイコンボタンから開く。隠しジェスチャーにはしない。
- エリア選択面は下から開く。エリアを選んだ時点で確認ダイアログを出さず、背景を即時に切り替える。
- 遷移先の素材は事前に読込む。準備できた時点で、現在の背景を維持したまま光、遠景、環境音を約0.6秒で重ね替える。カメラ移動、暗転、汎用ワープ演出は用いない。
- モーション軽減時のエリア切替は即時とする。

### H-2. タスクとグリモのデータ境界（確定）

- グリモが受け取るタスク情報は、完了数、連続達成、成長に必要な集計値に限定する。タスクの件名、期限、説明その他の本文情報をグリモ画面・3D世界へ渡さない。
- Google Calendarからの取込自体は報酬を発生させない。グリモア上でユーザーが明示的に完了にした予定・タスクは、取込元を表示・区別せず、完了報酬の対象とする。
- 報酬とグリモの成長寄与は、各タスクにつき初回の完了時だけに発生させる。タスクを未完了へ戻す操作は許可するが、再完了での重複獲得は発生させない。
- タスク追加・完了時の報酬表示とグリモ成長は、タスク保存が成功した後にだけ発生させる。保存失敗時には、報酬も成長も発生させない。
- 報酬を受け取った完了済みタスクを後から削除しても、獲得済みアイテムとグリモ成長は取り消さない。達成・収集の履歴は、タスク一覧と独立して保存する。
- タスク追加時に確定した報酬も、タスクを後から削除して取り消さない。追加・完了のいずれも、保存成功時に確定する一度きりの収集履歴として扱う。
- 機種変更を主目的にはしないが、JSONエクスポート／インポートでは、Googleの認可情報を除くタスク、報酬、グリモ成長、選択エリア、テーマ、音、モーションその他のアプリ保有状態を引き継げるようにする。同期基盤は設けない。

### H-3. 共有状態インターフェース（確定）

- タスク、報酬台帳、グリモ成長、背景エリア、表示設定は、それぞれのモジュールが永続データの唯一の所有者となる。他モジュールは所有データを直接更新しない。
- タスクモジュールは、保存成功後に `taskCreated` と `taskCompletedFirstTime` の型付きイベントを発行する。報酬台帳はこれを受けて一度きりの報酬を確定し、グリモ成長はタスク本文を受け取らない集計値だけを読む。
- Google Calendarからの取込結果はタスク・予定の正規化モジュールを経由し、画面へは出所を示さない共通形式として渡す。
- 下部ナビゲーション、シートの開閉、選択中の日付など短命な画面状態は画面内に閉じ込め、グローバルな永続状態に置かない。
- モジュール横断の書込みが必要な操作は、単一の永続化トランザクションで完了させる。保存成功後にのみイベント・演出を発火し、途中失敗では可視状態を変更しない。
- これに反するF-2の「下部の戻るボタンだけ」という記述は、下部ナビゲーションとエリア選択を置かないという意味ではなく、常設UIを最小限にする意図として扱う。F-6を優先する。

### F-7. カレンダーの月表示密度（確定）

- 月表示では、各日に予定・タスクの短い題名を最大2件まで直接表示する。3件目以降は件数で示す。

- 予定・タスクの色は、Google Calendar由来かどうかではなく、既存のタスク分類にだけ対応させる。分類なしは中立色とし、出所を示す色分けはしない。

### M-3. アイテム報酬の抽選（確定）

- タスク追加時・初回完了時のアイテム報酬は、タスク内容や難易度を分析せず、種類ごとに重みを持つランダム抽選で決める。

- タスク追加時と初回完了時は、同一のアイテムプールと同一の抽選重みを使う。報酬価値に差を設けない。

### M-4. 報酬表示の段階化（確定）

- アイテムの初取得時だけ、コンパクトな画面下部の報酬シートで、アイテム絵、名前、説明全文を表示する。上へ払うか外側をタップすれば閉じられる。

## H. アーキテクチャ方針（★確定・旧2ファイル未記載）

- 「細かく大量の更新・調整・変更を繰り返す」開発スタイルを想定し、**小さく独立したモジュール単位で実装する**方針を採用。C章で確定済みの「背景世界」「生物」の完全レイヤー分離とも思想が一致し、UIレイヤーを含めれば3層構造がベースになる。

- **品質段階**：性能判定モジュールが`full`／`reduced`を決定し、背景・グリモ・UIは同じ段階を購読して各自の縮退を行う。タスク、カレンダー、図鑑、IndexedDBの状態はこの契約に含めない。

## L-2. 犬系グリモ（水属性）デザイン仕様（確定）

O章にあった最優先の未決定事項を、2026-08-19の相談セッションで確定。

- **卵**：楕円形。氷/水晶のような半透明の殻。中でうっすら水色の何かが揺れて見える。
- **幼体**：まん丸プニプニの体型。ファンタジー要素（K章：発光に限らない）は輪郭・部位の形状と周囲エフェクトに宿す——耳・尻尾の先端だけがヒレ/水滴状の非現実的な形状になり、歩く/座ると足元にごく小さな波紋が出る。地色は淡く、水色は耳先・尻尾先など限定的な範囲にとどめる。
- **子供**：幼体の丸みと可愛さを残しつつ体型が成長し始める（プニプニ→ふっくら）。水色のグラデーションが背〜尻尾など体の一部に定着し始める（まだ部分的）。「幼体の延長」であることを優先し、別デザインに飛ばない。
- **成体**：オオカミ/ハスキー系をベースにした犬種（面長・スリムな体躯・垂れ気味の尻尾）。体全体が水色〜青のグラデーションで、はっきりと水属性と分かる配色。トーンは卵〜子供の「かわいい」路線から、成体で「かわいい＋かっこいい」が融合する方向へ転換する。
- **成長曲線**：卵→成体でプロポーションは大きく変化させる（幼体はまん丸プニプニ、成体は犬らしい骨格）。緩やかな変化ではなく、各段階ではっきり見た目が変わることを狙う。
- 決定の位置づけ：モデリング・リグ等の実装判断はまだ行っていない。上記はコンセプト・ビジュアル方針の確定であり、次はディテール（表情、模様の具体的な入り方、サイズ感など）を詰める段階。

## M-2. 図鑑・コレクションの二層構成（確定）

- コレクション画面は、**グリモ図鑑**と**アイテム図鑑**の二つを必要とする。
- **グリモ図鑑**：ランダム報酬ではなく、自分が出会い成長を見届けた存在の記録とする。各系統の卵・幼体・子供・成体を記録し、犬系グリモは実際の進化時に該当段階を解放する。他4系統はエリア追加や新しいグリモとの出会いで解放する。
- **グリモ図鑑の表示**：未発見の系統・段階は控えめな輪郭だけを表示し、成長の余地を示す。詳細では3Dグリモを主役に、段階、属性、初遭遇日、短い観察記録を表示する。全収集率ではなく各グリモの成長履歴を読む体験を優先する。
- アイテム図鑑は、タスク管理アクションに対する報酬として得たアイテムを記録する。グリモの成長段階や発見状態と混同しない独立のコレクションとする。
- **アイテムの役割**：v2初期版では収集・鑑賞専用とし、消費、強化、再抽選、エリア解放などのゲーム内効果を持たせない。タスクを終えた行動の記録と、発見の喜びを担う報酬として扱う。
- **獲得契機**：タスクを追加した時と、タスクを完了した時に報酬を得る。タスク管理そのものに小さな達成感を与える仕組みとする。
- **未発見品の扱い**：未発見のアイテムはシルエットや空き枠として表示しない。図鑑には獲得済みの品だけが追加される。
- **説明文**：各アイテムに、鑑賞の主役となる短い説明文を付ける。世界観を広げる興味深い文、少し笑える文など表現の幅を許容し、将来のアイテム追加もデータ追加だけで継続できる構成にする。
- **受取演出**：タスク追加時は、入力を遮らない小さな獲得表示（アイコン、品名、短い一文）にする。タスク完了時は、アイテム全体と説明文を読める少し大きな獲得演出にする。短時間に複数の報酬が生じる場合は最後の一件だけを表示し、残りは件数へまとめる。
- **重複品**：重複取得を許容し、各アイテムの総取得数と最終獲得日を記録する。説明文の大きな表示は初獲得時のみとする。
- **一覧構成**：アイテム図鑑には獲得済みの品を新着順のグリッドで表示する。分類タグ（自然物、古い遺物、用途不明の珍品など）をデータに持たせ、収録数が増えた段階で絞り込みへ利用する。
- ナビゲーションの入口は「図鑑」一つとし、画面内のセグメントで「グリモ」「アイテム」を切り替える。詳細な獲得条件・報酬テーブル・表示仕様はO章で継続して決める。

## S. 最高品質化の実装基準（確定・2026-08-19）

外部一次資料と公式実装を再調査した詳細仕様は
`Grimoire_最高品質化仕様.md` を正本とする。同書の **[外部仕様/事実]**、
**[採用判断]**、**[初期調整値]** を混同せず、初期値は実機・最終アセットで再調整する。

### S-1. モジュール境界と永続化

- 背景世界、生物、UI chrome、データストアは単独 owner を持ち、bootstrap 以外で
  相互の実装を import しない。背景が公開する immutable な光・tone・quality snapshot
  だけを生物と UI が読む。UI は command、データストアは commit 済み projection と
  event を公開する。area1-coral 試作の `version: 2` は bootstrap adapter だけが読み、
  packed sRGB を linear 値へ変換した製品契約 `schema: 3` を consumer へ公開する。
  adapterはdirectionを正規化し、nested tupleをcopy+freezeして不正なfinite/range/hexを拒否する。
- task、報酬、成長、outbox の関連書込みは一つの IndexedDB transaction へまとめる。
  演出は commit 前に開始しない。transactional outbox、決定的な `eventId`、15秒の
  owner lease、consumer inbox/ackにより複数tabの同時実行を抑え、永続効果を一度にする。
  視聴覚の再生自体はat-least-once + idempotent session keyと明記する。
  command receiptも同じtransactionへ保存し、曖昧commit後は同じcommandId/payloadHashで
  同じ結果を返す。別payloadでのcommandId再利用は拒否する。
- 旧DBはユーザー起点でsnapshotとSHA-256を先に作り、runId付きstagingだけへ書く。
  検証成功後のactivation transactionで初めて正本へcopyしてactiveへflipする。失敗時は
  未検証taskを公開せず、旧DB・snapshot・stagingを自動削除しない。
  同じsource+sourceHashは新runIdを作らず既存runをresume/returnし、native taskとは予約ID
  namespaceとmigrationRunId付きactive projectionで分離する。

### S-2. 適応品質

- 端末名を真値にせず、120 frame（最低60）の p20 FPS と scene draw call、triangle、
  post-pass を測る。4秒 warmup、2.5秒継続で full→reduced、8秒継続で復帰、15秒
  cooldown、同一 session の2回目縮退で reduced lock を初期契約とする。
- 初期閾値は 48/57 fps、scene draw 50/38、triangle 150k（受入許容 +2%）/100k、
  post-pass 10/8。full は DPR 1.5、reduced mobile は DPR 1.15・render scale .82 を
  上限とする。60fpsは固定capではなく最低校正基準とし、native refreshで描画する。
  Pixel 7a / Xiaomi 14T Pro 各5 run×60秒でp20/p5、100ms超stall、tier遷移を校正する。
  triangle予算はskyを除くvisible world geometryを数え、全passのrenderer trianglesは診断値に
  分離する。auto+reducedでwarmup後のp20<40が3秒継続、context loss、shader failure時は
  rendererを止め、asset不要の生成poster（任意video優先）へ切り替えてHTML操作を維持する。

### S-3. UI、theme、アクセシビリティ

- 共通 semantic token の上に「金属・石・文字階層」と「博物学・自然素材」の表現
  token を重ねる。表現層は contrast、focus、DOM順、accessible name を上書きしない。
- WCAG 2.2 AA を最低線とし、通常文字 4.5:1、large text 3:1、UI boundary / focus
  3:1 を最終合成 pixel で検証する。accent面は専用`onAccent` tokenを使う。icon-only nav は長押し tooltip に加えて常時
  `aria-label` を持たせ、keyboard、200% zoom、320 CSS px、reduced motion を受入試験にする。

### S-4. 3D / VFX / 生物物理

- linear-sRGB で照明・fog・VFXを合成し、ACES は最終 composite の一箇所だけで適用する。
  背景の key light direction / linear color / intensity / exposure を契約化し、生物側は
  clamp して補間する。god rays は radial post-process、fog は各world materialで一度だけ
  評価する解析的3-band depth/height fog、粒子はinstancingを既定とする。depth-reconstructed
  raymarchは現行baselineに含めず、desktop実験のDecision Candidateに限る。
- VRM / Live2D の耳・尻尾・毛先は別 profile とし、固定 timestep と substep、角度 clamp、
  collider を必須にする。詳細仕様の stiffness / drag / gravity / 最大角は校正用初期値で、
  最終リグなしに標準値と断定しない。

### S-5. マイクロインタラクションと音

- press は scale .972、y 2 px、押下 70 ms、release spring は stiffness 430 / damping 30 /
  mass .72 を初期値とする。8 px を超える drag は cancel し、保存失敗時は glow / reward を
  出さない。glow は最大 opacity .34、blur 14 px、420 ms の余韻を基準に背景光色へ同期する。
- 音は user gesture 後に開始し、phase-locked な ambient / harmonic / pulse stem を使う。
  BGM と SFX bus、EQ、fade、polyphony、voice stealing を詳細仕様どおり分離する。操作原因と
  視覚・SE・触覚は一対一 event で束ね、いずれを無効にしても操作結果を理解可能にする。
  compressor後にAudioWorklet true-peak limiterを置き、最大polyphony最終mixを-1 dBTP以下で
  検証する。outboxのcommittedAtはstaleness専用とし、claim時に新しいpresentationIdと
  monotonic presentationAtを発行してvisual/audio/creatureへ同じlookaheadで配る。

### S-6. 未決定と合格条件

- エリア遷移の最終採否、完成リグの spring 最終値、最終 HDR scene の VFX 値、mastering
  済み音源の mix 値、icon-only nav の初見理解は物理端末・実アセット試験後に確定する。
- 実装の合格条件と検証 ID は `Grimoire_最高品質化仕様.md` 第7章を使用する。
